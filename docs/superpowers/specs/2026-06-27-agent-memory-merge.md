## 3. turn_id Assignment

`turn_id` is auto-generated by `ingest()`. The developer never provides it.
**Each user message starts a new turn.** Everything else (assistant, tool_result)
belongs to the current turn.

```python
# User message → new turn:
tid_1 = core.ingest(role="user", content="What about fracking?", session_id="s1")
# → returns "a1b2c3d4e5f6" (new UUID)

# Assistant response → same turn:
core.ingest(role="assistant", content="Pennsylvania requires...", session_id="s1")
# → same turn_id "a1b2c3d4e5f6"

# Tool result → same turn:
core.ingest(role="tool_result", content="EPA data: ...", session_id="s1")
# → same turn_id "a1b2c3d4e5f6"

# Assistant speaks again → same turn:
core.ingest(role="assistant", content="Additionally, Ohio has...", session_id="s1")
# → same turn_id "a1b2c3d4e5f6"

# New user message → new turn:
tid_2 = core.ingest(role="user", content="Tell me more about Ohio", session_id="s1")
# → returns "b2c3d4e5f6a1" (new UUID)

# Compile a turn:
await core.compile_turn(turn_id=tid_1, timestamp="10:30", title="Fracking Discussion")
```

**Auto-generation logic in `ingest()`:**
```python
def ingest(self, role, content, session_id, ...):
    if role == "user":
        turn_id = str(uuid.uuid4())[:12]  # new turn
    else:
        turn_id = self._get_last_turn_id(session_id)  # same turn
    # ... store with turn_id
    return turn_id

def _get_last_turn_id(self, session_id: str) -> str | None:
    rows = self._db.query(
        "SELECT turn_id FROM messages WHERE session_id = ? ORDER BY ts DESC LIMIT 1",
        [session_id],
    )
    return rows[0]["turn_id"] if rows else str(uuid.uuid4())[:12]
```

- `ingest_turn()` — batch all messages for one turn, generates one `turn_id`:
  ```python
  tid = core.ingest_turn([
      {"role": "user", "content": "What about fracking?"},
      {"role": "assistant", "content": "Pennsylvania requires..."},
  ], session_id="s1")
  # All messages get the same turn_id
  # Returns: "a1b2c3d4e5f6"
  ```
  The developer is responsible for keeping the batch to a single turn
  (one user message + any number of assistant/tool messages).
  For multiple turns, call `ingest()` multiple times.

- `ingest()` returns the `turn_id` (not the message id). For non-user messages,
  it returns the existing turn_id (same value as the user message that started the turn).
- The developer stores the returned `turn_id` and passes it to `compile_turn()` later.

**`compile_turn()` uses the actual `session_id` from HybridDB:**
```python
async def compile_turn(self, turn_id: str, timestamp: str, title: str) -> None:
    rows = self._db.query(
        "SELECT id, role, content, session_id FROM messages WHERE turn_id = ? ORDER BY ts",
        [turn_id],
    )
    if not rows:
        return
    session_id = rows[0]["session_id"]
    messages = [{"message_id": r["id"], "role": r["role"], "content": r["content"]} for r in rows]
    await self._llm_compiler.compile_session(
        turn_id=turn_id,
        session_id=session_id,
        messages=messages,
        timestamp=timestamp,
        title=title,
    )
```

## 8. Integration Points

### HybridDB → LLM Compiler

The LLM compiler reads messages from HybridDB by `turn_id`:

```python
# HybridDB row → AgentMemory message dict
{
    "message_id": row["id"],       # HybridDB's UUID
    "role": row["role"],            # user, assistant, tool_result
    "content": row["content"],     # verbatim message text
}
```

`compile_turn()` queries by `turn_id` (not `session_id`) to get exactly one
turn's messages. The `session_id` is extracted from the query results and
passed to the compiler for citation purposes.

### AgentMemory Search

`search_memory()` is a separate method on `MemoryCore`:

```python
def search_memory(self, query: str, limit: int = 5) -> list[SearchHit]:
    return self._agent_memory_search.search(query, limit=limit)
```

`SearchHit` is imported from `coremem.agent_memory.bundle` (not `coremem.types`).
It has fields: `path`, `score`, `session_id`.

The agent uses `search_enhanced()` for raw message recall and
`search_memory()` for compiled knowledge. Both are available.

### Dreaming → MEMORY.md

Dreaming reads daily pages, promotes facts to MEMORY.md. MEMORY.md is loaded
at agent startup (boot memory). No HybridDB interaction needed.

`rebuild_index()` is called after every dreaming cycle to regenerate
weekly/monthly/index navigation files.

### Cross-Encoder Model

`CrossEncoderReranker` downloads `cross-encoder/ms-marco-MiniLM-L-6-v2`
(~80MB) on first `load()` call. Eagerly loaded in `MemoryCore.__init__()`.

## 9. Migration

Existing HybridDB data is unaffected. AgentMemory starts empty — it only
processes new turns after the merge. Old data can be backfilled by running
the compiler on historical sessions.

- `pages/` directory is removed — `daily/` replaces it
- `agent_memory/` directory is created at `{workspace}/agent_memory/`
- `.llm_cache/` and `.dreaming_cursor` live inside `agent_memory/`

**Test changes:**
- AgentMemory tests currently use `AgentMemoryBundle` with reference turn files
- After merge, tests should use `MemoryCore.compile_turn()` which reads from HybridDB
- Test fixtures need updating to write messages to HybridDB instead of reference files
- Existing `test_memorypack_compiler.py` tests use `apply_plan()` directly — these
