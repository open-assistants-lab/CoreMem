# MemoryPack End-to-End Flow

## Architecture

```
Agent Conversation (turn)
        │
        ▼
┌──────────────────────────────────────────────────────────────┐
│                    HYBRIDDB (raw messages)                     │
│  • All messages stored by role, date, session                  │
│  • Agent can search raw messages directly                      │
│  • Source of truth, immutable                                  │
└──────────────────────────────────────────────────────────────┘
        │
        ▼ (background, per-turn)
┌──────────────────────────────────────────────────────────────┐
│              LLM COMPILER (1 call per turn)                    │
│  • Reads raw messages from HybridDB                           │
│  • Receives turn timestamp in prompt (HH:MM format)            │
│  • Generates a section (not a full page):                     │
│    ## HH:MM - Title                                            │
│    [narrative summary]                                         │
│    **Claims:** [bullet list]                                  │
│    **Citations:** [numbered list]                             │
│  • Appends section to daily/YYYY-MM-DD.md                    │
│  • Date from turn timestamp (reference turn frontmatter)      │
│  • Creates daily page if not exists (frontmatter + heading)  │
│    Frontmatter includes agent_memory_version for lint compat    │
│  • Atomic append: snapshot daily page before write,           │
│    restore on failure (same pattern as per-turn rollback)     │
│  • Deterministic validation (quote check, role enforcement)   │
│  • Retry loop + quote-fixing post-processor                   │
│  • Cached by session content hash (unchanged)                 │
│  • NOTE: LLM prompt changed from "produce a page" to          │
│    "produce a timestamped section"                            │
└──────────────────────────────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────────────────────┐
│              JOURNAL (MD files, daily atomic unit)             │
│  daily/YYYY-MM-DD.md — each turn appends a timestamped        │
│    section with claims + citations                             │
│  weekly/YYYY-Www.md — generated by rebuild-index              │
│  monthly/YYYY-MM.md — generated by rebuild-index             │
│  index.md — generated by rebuild-index                        │
│  MEMORY.md — boot memory (critical facts, promoted by dreaming)│
│  DREAMS.md — diary analysis output (for human review)          │
│                                                               │
│  • pages/ directory REMOVED — no per-turn pages               │
│  • .embeddings/ directory REMOVED — not used                  │
│  • Existing pages/ files are IGNORED (not migrated)           │
│  • Each turn is a timestamped section within the daily page   │
│  • Weekly/monthly/index are navigation, rebuilt on demand     │
│  • Human-readable, LLM-readable, git-trackable                │
│  • Progressive disclosure: daily → section → claims           │
│  • No database — just flat MD files                           │
└──────────────────────────────────────────────────────────────┘
        │
        ▼ (on-demand: coremem dream or cron)
┌──────────────────────────────────────────────────────────────┐
│              DREAMING CONSOLIDATION (1 LLM call per cycle)    │
│  • Trigger: on-demand (coremem dream) or cron                 │
│  • Reads daily journal pages since last cycle                 │
│    (cursor stored in .dreaming_cursor file)                    │
│  • Input filtering: extracts only narrative summary text      │
│    (between ## HH:MM - Title and **Claims:**) for each        │
│    section. Strips claims and citations — they're structured  │
│    data, not analysis material.                                │
│  • Chunking: processes max 7 days per LLM call to avoid       │
│    context overflow. Multiple calls if more days pending.     │
│  • Dedup: checks DREAMS.md for existing ## YYYY-MM-DD         │
│    heading before appending. Skips if already analyzed.       │
│  • Error handling: validates LLM output has required          │
│    sections (Events, Emotional Patterns, etc.). If malformed,  │
│    retries once. If still malformed, logs error and skips.    │
│  • NOTE: cursor only tracks date, not individual sections.    │
│    If a daily page is updated after cursor date, the new      │
│    sections are missed. Acceptable for MVP.                   │
│  • LLM outputs markdown directly:                              │
│    ### Events                                                 │
│    - Discussed fracking regulations (10:30)                   │
│                                                               │
│    ### Emotional Patterns                                     │
│    - Frustration with industry self-monitoring               │
│                                                               │
│    ### Promoted to MEMORY.md                                  │
│    - User opposes fracking and advocates for a ban           │
│  • Promoted facts appended to MEMORY.md as bullet points     │
│    with date prefix:                                          │
│    - [2026-06-25] User opposes fracking and advocates for ban │
│  • MEMORY.md grows unbounded (pruning is future work)         │
│  • Full analysis appended to DREAMS.md                        │
└──────────────────────────────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────────────────────┐
│                    SEARCH (at query time)                     │
│  • BM25 + stemming + fuzzy matching (top 20)                 │
│  • Cross-encoder re-ranker (top 5)                           │
│  • ~400ms per query, deterministic, no API calls             │
│  • Searches daily pages only (weekly/monthly are navigation)  │
│  • Multi-section scoring:                                    │
│    1. Parse daily page into sections by ## HH:MM - Title      │
│    2. For each section, extract scoring text: narrative +     │
│       claims only (exclude **Citations:** block)              │
│    3. Score each section independently against query          │
│    4. Take max section score as page score                   │
│    5. Return top-5 pages                                     │
│  • _extract_sections() replaces _extract_claims():            │
│    - Old: parse # Current State blocks, return claim lines    │
│    - New: parse ## HH:MM - Title sections, return section     │
│      text excluding the **Citations:** block                   │
│    - Regex: r"^## (\d{2}:\d{2}) - (.+)$" for section starts  │
│    - Fallback: if no sections found, score full page text    │
└──────────────────────────────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────────────────────┐
│                    AGENT RESPONSE                             │
│  • Top-5 relevant pages injected into context                │
│  • Agent reads pages directly (progressive disclosure)       │
│  • Agent can also search HybridDB for raw messages           │
└──────────────────────────────────────────────────────────────┘
```

## Daily Page Format

```markdown
---
date: 2026-06-25
agent_memory_version: 1
---

# 2026-06-25

## 10:30 - Fracking Discussion

User asked about fracking's impact on groundwater in Marcellus Shale.
Assistant presented conflicting research on groundwater contamination.

**Claims:**
- Fracking's effect on groundwater is uncertain (conflicting research)
- Pennsylvania requires baseline testing before and after drilling
- User distrusts self-monitoring by fracking companies

**Citations:**
[1] User: "How has fracking affected the groundwater quality..."
[2] Assistant: "There is conflicting research on the effect..."

## 11:15 - Bachelorette Party Planning

User planning a bachelorette party weekend getaway to the beach in August.
Considering Santa Barbara, California. Wine and cheese tasting at a vineyard.

**Claims:**
- User is planning a bachelorette party for August
- User attended cousin's wedding at a vineyard on June 10th
- User prefers wine country themes for celebrations

**Citations:**
[3] User: "I'm thinking of Santa Barbara for the bachelorette..."
[4] Assistant: "The Santa Ynez Valley has several vineyards..."
```

## Daily Page Creation

When the compiler runs for a new day (determined by turn timestamp):

1. Create `daily/YYYY-MM-DD.md` with frontmatter:
   ```yaml
   ---
   date: YYYY-MM-DD
   agent_memory_version: 1
   ---
   ```
2. Add `# YYYY-MM-DD` heading
3. Append the timestamped section
4. Atomicity: snapshot the daily page before write, restore on failure
5. Do NOT update weekly/monthly/index — those are rebuilt by `coremem rebuild-index`

## LLM Prompt Change

The compiler prompt changes from "produce a MemoryPack page" to "produce a
timestamped section". The turn timestamp is passed in the prompt:

```
The current time is HH:MM. Produce a timestamped section for the daily journal:

## HH:MM - Title

[narrative summary of the conversation]

**Claims:**
- [claim with exact quote citation]

**Citations:**
[1] [role]: "[exact quote]"
```

The section is appended to `daily/YYYY-MM-DD.md`. The deterministic compiler
validates the claims and citations within the section (same exact quote check,
same role enforcement).

## Weekly/Monthly/Index Format

Generated by `coremem rebuild-index` (separate command, not part of compiler):

```markdown
# Week 26 (2026-06-22 to 2026-06-28)

- [2026-06-25](daily/2026-06-25.md) — Fracking discussion, bachelorette party
- [2026-06-24](daily/2026-06-24.md) — Charity events, anniversary planning
```

```markdown
# June 2026

- [Week 26](weekly/2026-W26.md) — Fracking, bachelorette, charity
- [Week 25](weekly/2026-W25.md) — Gift shopping, restaurant recommendations
```

```markdown
# MemoryPack Index

## 2026-06
- [Week 26](weekly/2026-W26.md)
- [Week 25](weekly/2026-W25.md)

## 2026-05
- [Week 22](weekly/2026-W22.md)
```

Navigation indexes only. No LLM synthesis. The agent reads the weekly page,
clicks into a daily page, reads the section.

**`coremem rebuild-index` behavior:**
1. Scan `daily/` directory for all `YYYY-MM-DD.md` files
2. For each file, read the first section title (text after first `## HH:MM - `)
   to use as the one-line description
3. Group by ISO week and month
4. Write `weekly/YYYY-Www.md` files with links to daily pages + descriptions
5. Write `monthly/YYYY-MM.md` files with links to weekly pages
6. Write `index.md` with links to monthly pages

## Section Parsing

Sections are delimited by `## HH:MM - Title` headings. The regex:

```python
SECTION_RE = re.compile(r"^## (\d{2}:\d{2}) - (.+)$", re.MULTILINE)
```

Each section is scored independently. The page's score is the max section score.
If no sections found, the full page text is scored as one document (fallback).

**`_extract_sections()` replaces `_extract_claims()`:**
- Old: parse `# Current State` blocks from per-turn pages, return claim lines
- New: parse `## HH:MM - Title` sections from daily pages, return section
  text excluding the `**Citations:**` block (citations are noisy for BM25)
- Regex for section starts: `r"^## (\d{2}:\d{2}) - (.+)$"` (multiline)
- Section end: next `##` or end of file
- Citations block: from `**Citations:**` to end of section — excluded from scoring
- Fallback: if no sections found, return empty list (score full page text)

## `apply_plan()` Refactoring

Old behavior:
- Write per-turn page to `pages/{page_id}.md`
- Update index, log, MEMORY.md

New behavior:
- Read existing `daily/{date}.md` (or create if not exists)
- Append timestamped section with claims + citations
- Write back to `daily/{date}.md`
- Atomicity: snapshot daily page before write, restore on failure
- Do NOT update weekly/monthly/index (handled by rebuild-index)

## Directory Cleanup

- `pages/` directory is REMOVED — no per-turn pages
- `.embeddings/` directory is REMOVED — not used
- Existing `pages/` files are IGNORED (not migrated, not deleted)
- Search only looks at `daily/` directory

## Dreaming Cursor

A file `.dreaming_cursor` stores the last processed date:

```
2026-06-25
```

The dreaming pass reads all daily pages after this date, processes them, and
updates the cursor to today. If the file doesn't exist, processes all daily pages.

**Limitation:** Cursor only tracks date, not individual sections. If a daily page
is updated after the cursor date, the new sections are missed. Acceptable for MVP.

## Dreaming Trigger

On-demand (`coremem dream`) or cron-triggered. Not automatic.

## Dreaming Input Filtering

Before passing to the LLM, the dreaming pass extracts only the narrative
summary from each section — the text between `## HH:MM - Title` and
`**Claims:**`. Claims and citations are stripped because they are structured
data, not analysis material. The LLM receives:

```
## 10:30 - Fracking Discussion

User asked about fracking's impact on groundwater in Marcellus Shale.
Assistant presented conflicting research on groundwater contamination.
```

Not the claims or citations.

## Dreaming Chunking

To avoid context overflow, the dreaming pass processes max 7 days per LLM call.
If more days are pending (cursor behind by 14 days), it makes 2 calls. Each
call produces a separate `## YYYY-MM-DD` entry in DREAMS.md.

## Dreaming Dedup

Before appending to DREAMS.md, check if `## YYYY-MM-DD` already exists. If so,
skip (already analyzed). This prevents duplicates when cursor is reset.

## Dreaming Error Handling

After the LLM response, validate that the output contains all required sections:
- `### Events`
- `### Emotional Patterns` (optional — may be empty)
- `### Behavioral Patterns` (optional)
- `### Cognitive Patterns` (optional)
- `### Context` (optional)
- `### Anomalies` (optional)
- `### Promoted to MEMORY.md` (optional)

If `### Events` is missing, retry once with the error message. If still
malformed, log the error and skip the day. Do not corrupt DREAMS.md.

## Dreaming System Prompt

```
You are a diary analyst. Read the daily journal entries and produce a structured
analysis. Focus on:

- Events: what happened
- Emotions: how the user felt
- Cognitions: what the user thought, how they reasoned
- Behaviors: what the user did, how they interacted
- Context: topics discussed, people mentioned
- Patterns: recurring themes across entries
- Anomalies: deviations from established patterns
- Contradictions: conflicting statements across entries
- Promoted facts: durable facts worth keeping in long-term memory

Output markdown with these sections. Be specific, reference timestamps.
```

## Dreaming Output

The LLM outputs markdown directly (not JSON). The dreaming pass appends this
markdown to `DREAMS.md` and extracts the `Promoted to MEMORY.md` section for
appending to `MEMORY.md`.

Promoted facts are appended to `MEMORY.md` with a date prefix:

```markdown
- [2026-06-25] User opposes fracking and advocates for a ban
- [2026-06-25] User prefers wine country themes for celebrations
```

No deduplication for MVP. If a fact contradicts an existing entry, both remain
until the agent or user resolves the conflict. MEMORY.md grows unbounded —
pruning is future work.

## DREAMS.md Format

```markdown
# Dream Diary

## 2026-06-25

### Events
- Discussed fracking regulations (10:30)
- Planned bachelorette party (11:15)

### Emotional Patterns
- Frustration with industry self-monitoring (fracking)
- Excitement about wine country plans (bachelorette)

### Behavioral Patterns
- User asks follow-up questions that dig deeper
- User prefers concrete examples over abstract

### Cognitive Patterns
- User weighs pros/cons before deciding
- User values environmental impact data

### Context
- User is planning multiple social events
- User is researching environmental policy

### Anomalies
- User asked for detailed explanation (usually prefers concise)

### Promoted to MEMORY.md
- User opposes fracking and advocates for a ban
- User prefers wine country themes for celebrations
```

## Date Determination

The compiler determines the date from the turn timestamp (from the reference
turn frontmatter, which was written from HybridDB), not the system clock. This
ensures that historical turns are appended to the correct daily page, even if
the compiler runs days later.

```python
turn_date = datetime.fromisoformat(turn_timestamp).strftime("%Y-%m-%d")
daily_path = root / "daily" / f"{turn_date}.md"
```

## Key Principles

1. **One LLM call per turn** — the compiler. No observation pipeline (9+ calls), no separate reflection pipeline.
2. **One LLM call per consolidation cycle** — the dreaming pass. Periodic, not per-turn.
3. **Deterministic validation** — exact quotes, role enforcement, lint. The compiler catches LLM errors.
4. **Flat MD files** — no database for compiled pages. Human-readable, git-trackable.
5. **Search is fast and cheap** — BM25 + cross-encoder, ~400ms, no API calls.
6. **Progressive disclosure** — agent reads daily page, drills into timestamped section, then claims.
7. **Two-tier memory** — journal (everything) + dreaming (what's important). No complex hierarchy.
8. **Diary study framework** — dreaming analyzes events, emotions, cognitions, behaviors, context.

## What We Removed

- Observation pipeline (9+ LLM calls per turn, no validation)
- Reflection pipeline (separate LLM calls, speculative)
- Per-turn pages (daily page is the atomic unit)
- `pages/` directory (replaced by `daily/`)
- `.embeddings/` directory (not used)
- HybridDB for compiled pages (over-engineering at this scale)
- Embedding index (worse than cross-encoder on this dataset)
- Four-tier hierarchy (journal → episodic → semantic → procedural)
- LIWC (outdated word-count tool, LLM does better analysis for free)
